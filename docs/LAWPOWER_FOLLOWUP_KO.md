# 로파워 회생/파산 수정안

대상: `lawtghsw-ctrl/maeil`, 기준 커밋 `db8f0b74d3de411103715767ec337363d3927d56`.
기존 전화번호 수정안에 이번 요청을 누적했습니다. 운영 반영, GitHub push/merge, 실제 DB 변경, 실제 문자 발송은 하지 않았습니다.

## 변경 내용

1. **영업자별 자동발송 설정 저장**
   - 문구, 자동발송 체크 상태, 발신번호, 이미지 경로가 저장 응답과 일치하는지 확인한 뒤 성공으로 표시합니다.
   - 저장 직후 전체 재조회 결과로 폼을 다시 덮지 않고, 확인된 저장 행으로 갱신합니다.
   - 조회/저장 오류를 명시적으로 표시하며 작성 중인 내용은 보존합니다. 초기 조회에 실패한 상태에서 기본값으로 덮어쓰지 않습니다.
   - 영업자를 바꿨다가 돌아와도 화면 내 미저장 초안을 보존하고, 중복 저장 및 로펌/권한 변경 중의 잘못된 저장을 방지합니다.
   - 로펌 공통 중복방지 시간은 변경한 경우만 별도로 저장합니다. 담당자 저장을 이유로 로펌 공통 문구/체크 상태를 덮지 않습니다. 공통 시간만 저장에 실패하면 담당자 저장 성공과 구분해서 알립니다.
2. **문구 템플릿**: 제목을 누르면 내용이 펼쳐지는 박스형 목록으로 바꿉니다. 키보드 조작 및 기존 사용/삭제 기능을 유지합니다.
3. **자동발송 이미지**: 드래그 앤 드롭과 클릭 파일 선택을 모두 지원합니다. JPEG/PNG/GIF, 최대 3장, 합계 2 MB 제한 및 실제 파일 형식을 검사하고, 미리보기/제거/저장된 이미지 재표시를 제공합니다. 기존 비공개 `sms-media` 저장소와 로펌 권한을 사용하며 새 공개 권한이나 자격증명은 만들지 않습니다.
4. **상담일지 PDF**: A4 세로, 한글 글꼴 내장, 본문 10 pt(기존 9 pt), 항목명 9 pt를 사용합니다. 좌우 여백 9 mm, 줄/표/제목 간격 축소, 중복 표제 제거, 메모 전폭 배치로 페이지를 줄입니다. 한 장 강제 축소나 내용 생략은 하지 않으며 긴 기록은 자동으로 다음 페이지에 이어집니다. 첨부파일은 기존과 같이 목록만 출력합니다.
5. **DB관리**: 고객 행의 ‘컨택 · 사유’ 버튼만 데스크톱/모바일에서 제거합니다. 기존 저장 기록, 컨택 알림 계산, 문자발송/상담일지/메모 기능과 다른 화면의 기능은 보존합니다.
6. **미상담 컨택 경고**: `미상담` 단계는 당일 부재중 기록 1회로 경고를 해제합니다. DB 고객행/상단 경고 수와 대시보드 컨택 필요 수/할 일에 동일하게 적용합니다. `부재`는 기존 2회, `착수금 안내`는 1회, `장기부재`는 3일 주기를 유지합니다. 통화 연결(기존 재통화 태그) 해제, 메모 집계/삭제 처리, KST 다음 날 초기화 규칙은 바꾸지 않습니다.
7. **기존 전화번호 수정안 유지**: DB 상담일지 및 고객 상세의 수기 수정, 검증, 권한 검사, 연결된 DB/고객의 원자적 동기화를 포함합니다. 상세 사항은 `docs/CUSTOMER_PHONE_EDIT.md`를 참고하세요.
8. **DB관리 하단 가로 이동**: 데스크톱 고객리스트가 창보다 넓으면 화면 맨 아래에 좌우 이동 막대를 표시합니다. 표 끝까지 아래로 내리지 않아도 드래그하거나 방향키/Home/End로 숨겨진 열을 볼 수 있습니다. 기존 표의 가로 스크롤과 양방향으로 동기화하고 창 크기가 바뀌면 다시 맞춥니다. 표가 창에 들어가면 숨기며 모바일 카드 보기와 상단 상태판의 기존 스크롤은 유지합니다. 팝업이 열려 있을 때는 하단 막대를 숨기고, 마지막 내용이 막대에 가리지 않도록 여유 공간을 둡니다.
9. **본인취소 상태**: DB관리의 상담 단계 목록에서 `불가` 바로 아래에 `본인취소`를 추가합니다. 상단 상태판/데스크톱·모바일 선택 목록/상담일지에 동일한 목록을 사용하며 선택·저장·재조회·필터를 지원합니다. 기존 기록은 바꾸지 않습니다. 이 값은 JSONB의 `detailStage`로 저장되어 추가 SQL이 필요하지 않습니다. 내부 호환용 `status`를 임의로 `거절` 등으로 바꾸거나 새 Meta/SMS 규칙을 만들지 않습니다. 따라서 기존 내부 status 기반 일부 집계의 분류도 그대로 유지되며, 이를 종결 분류로 바꾸는 것은 별도 업무 규칙 결정 사항입니다.

## 확인된 재현 경로와 운영 확인 한계

원본 커밋의 실제 React 화면을 오프라인에서 실행해 다음 경로를 재현했습니다.

- 담당자 문구/체크 상태 저장은 성공합니다.
- 직후 담당자 설정 재조회에 오류가 발생합니다.
- 기존 코드는 이 조회 오류를 무시하고, 다른 조회 결과로 폼 재설정이 실행되면서 이전 담당자 행/기본값으로 표시를 되돌립니다.

수정안은 저장 응답을 확인하고 이 재조회 덮어쓰기를 제거합니다. 조회 오류도 사용자에게 보이도록 처리합니다. 운영에서 해당 조회가 실패한 구체적인 원인은 인증된 재현/로그 없이는 확정하지 않았습니다. 이후 배포 사전 점검에서 대상 운영 DB의 기존 SMS 테이블/필수 열, 조회·저장 권한, 비공개 이미지 저장소 정책이 존재함은 읽기 전용으로 확인했습니다. 새 권한을 추가해서 오류를 숨기지 않았습니다.

## 합성 PDF 비교

같은 합성 입력으로 비교했습니다. 실제 고객정보는 사용하지 않았습니다.

- 짧은 일반 상담: 2쪽 → 1쪽
- 여러 항목을 채운 상담: 4쪽 → 2쪽
- 기대출 25건과 긴 메모 스트레스 입력: 10쪽 → 7쪽

입력 분량에 따라 쪽수가 달라집니다. 한 장에 맞추느라 글씨를 축소하지 않습니다.

## 적용 전 확인

- 이번 SMS/UI/PDF 수정에는 새 DB 마이그레이션이 필요하지 않습니다. 저장소의 기존 SMS 테이블/권한/이미지 관련 마이그레이션이 적용되어 있어야 합니다.
- 누적된 **전화번호 수정 기능에는** `supabase/migrations/20261021034000_customer_phone_edit.sql`이 필요합니다. 정상적인 검토/스테이징 절차로 SQL을 먼저 확인하고 적용한 뒤 앱을 반영하세요. 기존 데이터 일괄 변경은 없습니다. 운영 DB의 함수 기본 권한을 고려해 PUBLIC뿐 아니라 anon/authenticated/service_role의 자동 부여 권한을 명시적으로 회수하고, 검증된 관리자용 RPC만 authenticated에 실행 권한을 부여합니다. 실제 적용 상태는 별도 배포 결과를 확인하세요.
- 스테이징에서 담당자별 문구/체크 상태 저장 → 다른 화면 이동 → 재접속, 두 담당자/두 로펌 분리, 권한 없는 계정, 이미지 업로드/제거/재조회, 전화번호 연결 동기화와 PDF 다운로드를 확인하세요.
- DB 고객리스트를 좁은 데스크톱 창과 최대화한 창에서 열어 하단 좌우 이동, 표 자체의 가로 스크롤, 팝업 열기/닫기, 모바일 카드 보기를 확인하세요.
- 실제 문자 발송을 켜거나 발송 테스트를 하는 작업은 별도 승인 범위입니다. 설정 저장 테스트만으로 실제 발송이 확인된 것은 아닙니다.

## 검증 재실행

전체 회귀 검사 일부는 과거 커밋과 비교하므로 ZIP만이 아닌 Git 이력이 있는 체크아웃에서 실행하세요. 테스트 의존성은 앱에 추가하지 않고 별도 경로에 둡니다.

```sh
npm install --package-lock=false
npm install --prefix ../store-test-runtime --no-save --package-lock=false react@18.3.1 react-test-renderer@18.3.1
npm install --prefix ../sms-sql-check --no-save --package-lock=false @electric-sql/pglite
node --test --test-concurrency=1 tests/*.test.cjs
node --test --test-timeout=20000 --test-concurrency=1 services/sms-relay/test/*.test.mjs services/sms-relay/test/*.test.cjs
npx tsc --noEmit --incremental false
NEXT_TELEMETRY_DISABLED=1 npm run build
```

PDF 검사는 `pdfinfo`와 Python `pypdf`가 필요합니다. 합성 PDF 생성 명령 및 관련 검사는 PDF 테스트/스크립트를 참고하세요. 브라우저/실서비스 E2E는 이 오프라인 검증에 포함되지 않습니다. 독립 `npm run lint`는 저장소에 ESLint 설정이 없어 초기 설정 질문이 표시되므로 통과로 보고하지 않습니다.
